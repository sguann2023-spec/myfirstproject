# 旅行混剪

这是一个旅行短视频制作技能。默认只需要用户给出旅行主题和旅行素材视频，技能先按攻略口播风格生成文案，再按素材内容和时间轴生成一套竖屏旅行混剪视频。

## 限制

- 默认输入必须有旅行主题和旅行素材视频。主题可以是目的地、天数、人群、预算或玩法，例如“潮汕五天四晚亲子游”。
- 旅行素材至少 1 条，优先使用视频；图片也可以混用。素材可以是本地图片或者视频，也可以是视频、图片链接；素材总个数不超过20，总时长不超过20分钟。为避免逐条理解产生过长上下文，视频素材原则上不超过20条；超过20条时直接停止并请用户先筛选素材。
- 用户没有给主题时，先问主题；没有给旅行素材时，先问素材。缺任一项时不创建草稿、不生成配音。

## 执行步骤

> **严格顺序执行规则**：每个步骤必须完全执行成功并确认结果后，才可以进入下一步。禁止跳步、禁止在异步任务未完成时提前执行后续步骤。特别是：
> - 第 4 步（生成音频）必须拿到音频 URL 后才能进入第 5 步。
> - 第 5 步（识别字幕）必须拿到完整字幕分段时间轴后才能进入第 6 步。
> - 第 9 步（字幕模板）必须等待任务状态变为 `success` 后，才能进入第 10 步。
> - 每一步遇到错误或超时时，必须先重试或诊断失败原因，不得在未解决的情况下继续后续步骤。

1. 检查限制。必须先确认有旅行主题和旅行素材；素材至少 1 条、不超过 20 条、总时长不超过 20 分钟。缺主题或缺素材时先询问；素材条数超过 20 时直接停止并说明原因。获取总时长的方式：先判断每条素材是本地文件还是网络链接；本地文件直接用本地路径，网络链接直接用 URL；然后调用 `scripts/calc_total_duration.py` 脚本计算总时长（该 Python 脚本同时支持本地文件路径和远程 URL，内部使用 ffprobe 逐条获取时长并汇总），总时长超过 20 分钟时停止并说明原因。这一步必须用脚本固定实现，不依赖人工估算，确保结果稳定可复现。调用方式：
   ```bash
   python3 scripts/calc_total_duration.py <file_or_url_1> <file_or_url_2> ...
   ```
2. 理解视频素材内容并并发保存结果。**先检查工作区 `video_understanding/` 目录中是否已存在对应素材的理解结果文件**（按文件名前缀的三位序号匹配），对已有理解结果的素材跳过，不再重复发起理解任务；仅对尚未有理解结果的素材执行后续操作。采用并发方式处理视频素材，一次并发数量不超过 15：先判断每条视频是不是本地文件；如果是本地文件，先并发上传成临时视频链接（一次最多 15 个并发上传），然后并发理解这些视频（一次最多 15 个并发理解任务）；每个视频理解成功并取得完整文字理解结果后，必须立即写入工作区的 `video_understanding/` 目录，每条视频单独保存为一个 UTF-8 Markdown 文件，文件名使用三位素材序号和经清理的原文件名，例如 `001-海边日落.md`，至少记录素材序号、原始文件名或 URL、临时上传 URL（如有）、理解任务 ID、完整理解结果。**理解结果必须按 0.3 秒为最小时间粒度逐段描述画面内容**，例如“0~0.3秒：海边栈道上游客迎着海风慢走”、“0.3~0.6秒：镜头掠过海面和远处日落”，依次类推覆盖整条素材的每一个 0.3 秒区间，确保后续分镜匹配时能精确定位到 0.3 秒级的画面片段。如果素材总数超过 15，分批处理，每批最多 15 个并发。不要把所有完整返回结果长期保留在对话上下文中；后续生成文案和分镜时按需读取结果文件，并优先使用各文件中的内容摘要和时间段信息。每次理解视频可能比较慢，大约需要 1~5 分钟；所有视频都必须取得文字理解结果并成功保存，任一视频没有理解结果或保存失败时停止。
3. 生成攻略口播文案。用户没有给口播文案时，先根据主题和第 2 步得到的视频理解结果自动生成文案。**文案生成必须严格遵循“先规划画面时长、再按字数写文案”的流程，确保每句文案的字数与其对应画面的时长严格匹配。**具体步骤如下：
   **3a. 提取可用画面片段清单**：从第 2 步的视频理解结果中，按 0.3 秒粒度提取所有可用画面片段，汇总成一份“可用画面清单”，每条记录包含：素材序号、时间段（如 0~2.5秒）、画面内容摘要。将语义连续的多个 0.3 秒片段合并为一个“画面段”（如 0~2.5秒的连续画面合并为一个段），每个画面段的时长必须 ≥ 1.5 秒。
   **3b. 规划画面段与口播时长的对应关系**：中文旅行攻略口播的语速约为**每秒 4～5 个字**（含标点停顿）。根据素材内容和计划口播节奏，从可用画面清单中选出 8～12 个画面段，为每个画面段分配目标口播时长（1.5～3.5 秒），并计算该时长内最多能说多少字（画面段时长 × 4.5 = 最大字数）。所有画面段的目标时长之和应与最终口播总时长一致。
   **3c. 逐段撰写文案**：按规划的画面段顺序，为每个画面段撰写对应口播文案。**每句文案的字数必须严格不超过该画面段的最大字数限制**（即 画面段时长 × 4.5）。例如：某画面段分配 2 秒，则对应文案不能超过 9 个字；分配 3 秒，则不能超过 13 个字。绝不允许出现一句文案跨越多个画面段、或一个画面段内塞入过多文字的情况。
   **3d. 输出「文案-画面时长对照表」并校验**：文案写完后，必须输出一份对照表，逐行验证每句文案的字数是否在其画面段的字数限制内。如果任何一句超出限制，必须立即修改文案（缩短句子或增加该画面段的时长），直到全部通过校验。

   | 画面段 | 素材 | 时长 | 最大字数 | 文案内容 | 实际字数 | 是否通过 |
   |--------|------|------|----------|----------|----------|----------|
   | 段1 | 素材1 0~2.5s | 2.5s | 8字 | “第一次来先看这条” | 8字 | ✅ |
   | 段2 | 素材2 1.0~4.0s | 3.0s | 10字 | “两天一晚也能玩得很满” | 10字 | ✅ |

   最终成片时长以实际口播和分镜规划结果为准，文案总字数随实际时长灵活控制，但必须保证每句文案都满足对应画面段的字数上限。文案风格提示词（严格按以下风格特征生成，不得引用任何示例中的具体地名、景点或人物）：
   - **开头**：用一个设问句制造悬念，紧跟一句肯定回答，语气轻快有感染力，一秒抓住注意力。
   - **引导收藏**：紧接着用一句话引导收藏，并点出天数、预算或玩法亮点；没有精确数字时跳过具体数字，不要硬编。
   - **人物引入**（可选）：用一句话简要介绍出行人物和来源，增加真实感和代入感；没有真实人物信息时跳过，不要硬编。
   - **行程定调**：用一句话概括行程安排特点（如不赶不累、适合周末、主打拍照出片、吃逛都顺路等），传递轻松感和可执行性。
   - **分站点/玩法展示**：按画面素材顺序，用短句逐一描述 2～4 个核心亮点（景点、路线、玩法、住宿氛围、夜景、美食打卡等），每句突出一个真实可见的视觉记忆点，必须基于素材真实画面。
   - **预算/性价比锚点**（可选）：如果素材或主题中有明确预算、人均或交通信息，用一句话点出性价比；没有精确数字时跳过，不要硬编。
   - **结尾互动**：用一句引导收藏、评论或私信的话收尾，制造行动转化。
   - **整体语气**：口播攻略体，节奏快、信息密度高、每句都有画面感，像在跟朋友面对面安利一条值得照着走的路线。
   - 没有精确数字信息时不要硬编数字。文案字数根据实际口播总时长灵活控制，不要为了凑字数牺牲画面匹配和节奏。
4. 将口播文案生成音频，使用音色gv_989402eaac7b421ca713864f2da2aeb8，成功后必须取得口播音频 URL，没有音频 URL 时停止。
5. 识别字幕。识别第 4 步生成的口播音频字幕，固定使用 LLM 档位，成功后必须取得完整文本和分段字幕时间轴，没有字幕分段时停止。
6. 生成分镜计划。**必须以第 3 步的「文案-画面时长对照表」为骨架**，结合第 5 步的字幕时间轴，生成分镜计划。具体规则：
   - **分镜的时间轴必须以字幕时间轴为准**：第 5 步 ASR 识别出的每段字幕的起止时间，直接决定每个分镜在目标轨道上的 `start` 和 `end`。如果字幕分段过粗（如一大段包含多句文案），需按文案句子的自然断句进一步拆分，拆分后的时间按比例分配。
   - **分镜的画面来源必须复用第 3 步的规划**：第 3 步已经为每句文案预分配了画面段（素材序号 + 时间段），分镜计划必须直接使用这些预分配结果，不得重新随意匹配。例如第 3 步规划“段3 = 素材2 的 0~2.8秒”，则对应分镜的 `source_clip`、`source_start`、`source_end` 必须与此一致。
   - **画面内容必须与文案语义匹配**：每一句口播对应的画面必须是视频理解结果中真实存在的场景。例如口播写“沿海公路一路开过去”，则对应素材的画面中必须确实有沿途路景、车窗视角或海岸线画面。如果某句口播在所有素材中都找不到画面匹配的内容，应修改口播文案使其与实际素材画面吻合。
   - 计划必须覆盖完整时间轴、只使用真实素材索引，且时间片段必须完全连续：首段 `start=0`，每段 `start` 必须等于上一段 `end`，最后一段 `end` 必须等于总时长，不能有空隙、负时长或重叠。每个分镜时长必须控制在 **1.5 秒到 3.5 秒之间**，超出 3.5 秒的分镜必须拆分为多个子分镜，不足 1.5 秒的分镜必须与相邻分镜合并。
   - 每个分镜还必须同时生成**原素材截取片段**（`source_start` 和 `source_end`），表示从该素材中截取的起止时间。**原素材截取片段必须在该素材的实际时长范围内**：`source_start` 必须 ≥ 0，`source_end` 必须 ≤ 该素材的总时长（从第 2 步视频理解结果中获取的时长）。如果 `source_end` 超出素材实际时长，该分镜计划无效，必须重新调整截取范围，不得提交执行。
   - 注意：源片段时长（`source_end - source_start`）**不要求等于**目标时间轴上的分镜时长（`end - start`），因为字幕时间轴决定了分镜在目标轴上的位置，而源片段的选取是根据画面内容决定的，两者天然可能不一致。系统会根据 `starts/ends`（原始视频截取起止时间）和 `target_starts/target_ends`（目标轨道起止时间）的差值自动进行变速处理，无需手动计算速度。
   - 解析模型分镜后只允许做轻量边界校正：例如把最后一段补齐到总时长，或把毫秒级相邻边界对齐；不得因为很小的尾差丢弃语义匹配更好的计划。
   - 分镜计划生成完成后，必须将完整的分镜计划以 **固定 JSON 格式**保存到工作空间文件 `storyboard.json` 中。JSON 结构定义如下：

   ```json
   {
     "storyboard": [
       {
         "shot_index": 1,
         "start": 0.0,
         "end": 2.5,
         "source_clip": 1,
         "source_file": "broll_real_1.mp4",
         "source_start": 0.5,
         "source_end": 3.0,
         "description": "分镜画面内容描述",
         "subtitle_match": "对应的口播字幕文本"
       }
     ],
     "total_duration": 42.6
   }
   ```

   **字段说明**：

   | 字段 | 类型 | 必填 | 说明 |
   |------|------|------|------|
   | `shot_index` | integer | ✅ | 分镜序号，从 1 开始递增 |
   | `start` | float | ✅ | 分镜在目标时间轴上的开始时间（秒），首段必须为 0 |
   | `end` | float | ✅ | 分镜在目标时间轴上的结束时间（秒），必须等于上一段的 `start`，末段必须等于 `total_duration` |
   | `source_clip` | integer | ✅ | 素材序号，对应第 2 步理解结果的素材编号（1-based） |
   | `source_file` | string | ✅ | 素材原始文件名，如 `broll_real_1.mp4` |
   | `source_start` | float | ✅ | 从原素材中截取的开始时间（秒），必须 ≥ 0 |
   | `source_end` | float | ✅ | 从原素材中截取的结束时间（秒），**必须 ≤ 该素材的总时长** |
   | `description` | string | ✅ | 分镜画面内容描述，基于第 2 步视频理解结果撰写 |
   | `subtitle_match` | string | ✅ | 该分镜对应的口播字幕文本片段，用于校验音画同步 |
   | `total_duration` | float | ✅ | 整个分镜计划的总时长（秒），等于最后一段的 `end` 值 |

   **校验规则**（生成后必须自检，不通过则重新生成）：
   1. 时间连续性：`storyboard[0].start == 0`，`storyboard[i].start == storyboard[i-1].end`，`storyboard[-1].end == total_duration`
   2. 素材有效性：`source_start >= 0` 且 `source_end <= 对应素材的总时长`
   3. 时长合理性：每个分镜时长 `end - start` 在 1.5s～3.5s 之间
   4. 素材覆盖：所有素材至少被使用一次（如素材数量允许）

   后续第 10 步直接读取该文件执行，不再重新计算分镜。
7. 校验分镜计划与口播文案匹配。逐条检查第 6 步生成的分镜计划中每个分镜的 `description`（画面内容描述）是否与对应的 `subtitle_match`（口播字幕文本）在语义上一致。校验规则：①口播文案中提到的动作（如“坐船”“徒步”“看日落”“逛夜市”等）必须在对应素材的视频理解结果中有真实画面支撑；②口播文案中提到的场景（如“海边”“古镇”“观景台”“民宿露台”等）必须与素材实际拍摄场景一致；③不得出现口播描述了某个动作或场景但画面中实际没有的情况。如果发现不匹配的分镜，必须修正：可以更换素材片段、调整 `description` 使其如实描述画面、或修改口播文案使其与实际画面吻合，修正后重新校验直到全部通过。校验通过后输出一份校验报告，列出每个分镜的口播文案、画面内容、是否匹配及修正说明。
8. 创建草稿。创建竖屏草稿（1080x1920），封面可选，成功后必须取得草稿 ID 和草稿 URL。
9. 添加字幕模版。从下面四个字幕模板 ID 中随机选一个，对第 4 步生成的口播音频使用字幕模板识别，并将识别结果添加到第 8 步创建的已有草稿中。注意：使用字幕模板的同时必须将口播音频也添加到草稿中（`addMedia=true`），确保配音音频和字幕一起写入草稿。可选模板 ID：asr_1f9c8d7e6a2b4c0d9e8f123456789abc, asr_6a4f2c9e8b1d4f7aa3c5e9d02b6f8c13, asr_9d550677d16a4c879a19bfeee1623a38, asr_e7c1a9d4b6f24c8e91a3d5b7f0c2e6a8。
10. 添加画面素材。先运行 `scripts/prepare_batch_video.py` 脚本读取第 6 步生成的 `storyboard.json`，自动完成以下工作：解析每个分镜的素材路径、通过 ffprobe 获取各素材原始总时长、校验分镜时间连续性、校验 `source_end` 是否超出素材实际时长，最终输出 `add_batch_video` 所需的全部参数（JSON 格式）。脚本**必须确保以下两点**：①**目标视频轨道上的时间必须连续无空隙**——即每个分镜的 `target_start` 必须等于上一个分镜的 `target_end`，首段 `target_start=0`，最后一段 `target_end` 等于总分镜时长，不允许出现任何时间间隙，如果分镜之间存在间隙，脚本必须自动消除（将后续分镜的 `target_start` 前移到与前一个分镜的 `target_end` 对齐）；②**`durations` 参数必填**——每个视频片段必须传入该素材的原始总时长（脚本已通过 ffprobe 自动获取，单位为秒），不是目标时间轴上的播放时长，否则 API 会报“视频时长无效: 0.0”错误。脚本执行成功后，使用返回的参数调用批量添加视频接口（`add_batch_video`）一次性将所有分镜的视频片段添加到草稿中。目标时间轴位置通过 `target_starts`/`target_ends` 数组指定（表示目标轨道的开始/结束时间）。系统会根据源片段时长和目标时长的差值自动进行变速处理，无需手动传递 `speed` 参数。**`target_starts` 和 `target_ends` 必须同时传递**（都是数组），只传其中一个会报“需要同时传入数组，或同时不传”错误。**⚠️ 必须设置 `volume=-60`（静音）**，避免原始视频声音干扰配音和背景音乐。批量添加和单条添加都需要传此参数。如果批量添加失败，则回退为逐条串行添加作为兜底方案。发生素材轨道冲突时先修正时间轴，只在明确轨道重叠错误时重试备用轨道。关于 `durations` 参数的详细说明和示例见下方“常见问题 → 1. `add_batch_video` 批量添加视频失败”。
   ```bash
   python3 scripts/prepare_batch_video.py <storyboard.json路径> <素材目录路径>
   ```
11. 添加背景音乐。背景音乐从 `references/bgm.md` 里随机选一个，再写入草稿。背景音乐的时长必须与第 4 步生成的配音音频时长一致。添加音频时，截断通过 `start` 和 `end` 参数控制（表示从原始素材中截取的起止时间），`duration` 是原始素材的总时长（不可用于截断）：如果背景音乐时长超过配音时长，设置 `start=0`、`end=配音时长` 即可截断多余尾部；如果背景音乐时长不足配音时长，需要多次调用添加音频接口循环拼接，每次通过 `start` 和 `end` 指定从原始素材中截取的片段范围，直到覆盖完整配音时长（最后一段的 `end` 截断到精确对齐）。背景音乐轨道为 `bgm_audio`，音量设置为 `3`。
12. 最终校验。检查草稿脚本内容；检查是否有空隙、是否连续、字幕、配音、背景音乐是否都加上了。
13. 下载草稿。调用下载接口将第 8 步创建的草稿下载到本地，必须传入草稿 ID 和草稿名称。
14. 返回结果。展示思考切片的关键环节，不展示请求回包的具体细节。最终输出必须包含草稿下载链接。并且直接触发下载这个草稿。

## 常见问题

### 1. `add_batch_video` 批量添加视频失败

**现象**：调用 `add_batch_video` 时返回错误或片段未正确添加到草稿中。

**原因**：批量添加视频时，每个片段必须同时设置 `durations` 参数（表示该视频素材的**原始总时长**），否则接口无法正确识别素材，导致添加失败。

**解决方法**：在 `add_batch_video` 调用中，为每个片段显式传入 `durations` 数组，值等于该视频素材的**原始总时长**（通过 `get_media_duration` 获取，单位为秒），而不是时间线上的播放时长。示例：

```json
{
  "video_urls": ["素材路径1", "素材路径2"],
  "starts": [0, 5.0],
  "ends": [3.0, 8.0],
  "durations": [15.2, 12.8],
  "target_starts": [0, 3.0],
  "target_ends": [3.0, 6.0]
}
```

其中 `durations[i]` 是第 i 个视频素材的原始总时长（通过 `get_media_duration` 预先获取），`starts[i]` 和 `ends[i]` 定义从原始素材中截取的片段范围，`target_starts[i]` 和 `target_ends[i]` 定义在时间线上的放置位置。
